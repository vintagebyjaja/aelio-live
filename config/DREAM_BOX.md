# AELIO v1.0.2 — Dream Box configuration and manual rollout

This update extends the v1.0.1 candidate; none of these instructions has been executed against production.

1. Keep automatic Cloudflare builds/preview deployments disabled for `codex/migration-v1.0.2`. A GitHub branch push can otherwise trigger external integrations even without a workflow in the repository. The local source contains no GitHub Actions workflows, but dashboard settings have not been inspected. Never merge into main as part of delivery.
2. Back up and validate the existing shared Supabase project. If v1.0.1 migrations are already applied, run only `20261029000004_appearance.sql` after them. It adds JSON appearance columns and an inherited/custom mode without replacing existing records. Existing owner-scoped RLS and server-only writes remain. New installations must first follow the existing v1.0.1 SQL order and PATHD preservation instructions in SETUP.md. Do not reinitialize data or create another project.
3. Existing Supabase and R2 settings are unchanged. No new privileged keys are required for appearance. Preferences are global AELIO-only fields on `app_preferences`; PATHD keeps its own brand and subscriptions. Agent settings are on `app_agents`. Group conversations resolve against global settings, avoiding ambiguous multiple-agent inheritance.
4. Run `npm ci`, `npm run build`, `npm run typecheck`, `npm test`, `npm run check` from AELIO. This source update ZIP excludes generated HTML and compiled JS/CSS as requested. The build is essential before any owner-managed Cloudflare upload. The existing committed public artifacts are regenerated locally and preserved in the migration branch for the repository's current static-assets architecture.
5. Dream Box is now `/` and `/chat/`; the original approved marketing homepage is preserved at `/explore/`. Other marketing, Brain, Studio, account and authentication routes remain. `npm run build` generates both home experiences; `build:chat` updates the app shell only.
6. Weather/location routes use fixed public Open-Meteo endpoints (`api.open-meteo.com` and `geocoding-api.open-meteo.com`) with timeouts and no third-party browser keys. Review the provider's current usage/licensing/capacity terms for the intended production use before enabling the rollout. No live-provider account/production traffic has been validated. Adapt the isolated provider module if your approved commercial provider differs. Failure is shown as unavailable, never as sample conditions. Geolocation requires HTTPS and the user's permission; manual city search is available. Location coordinates are transient and not written to profiles or application logs. Requests disclose the selected coordinates/place to Open-Meteo. Attribution links are shown.
7. `_headers` permits geolocation on the same origin and blob image URLs for authenticated private backgrounds. The browser still prompts for location. Generated photographic assets are local, WebP-optimized and cached for a day. No external image host is needed.
8. Restaurant searches and directions open clearly labeled Google Maps links. No restaurant availability, travel time or traffic feed is invented. Groove Guide and VYBR8 have modular entry points; actual APIs and explicit-consent account linking are not connected because no real integration configuration exists in this source. Quick News asks the existing engine for attributed current sources and explicitly requires it to acknowledge unavailable live access. No new news provider is implied.
9. Speech input uses browser SpeechRecognition when supported and the browser's microphone permission. Audio may be processed by the browser vendor. The interface discloses this; unsupported browsers have a text fallback. The transcript only prepares a draft. This does not add voice inference or change the existing engine's capabilities.
